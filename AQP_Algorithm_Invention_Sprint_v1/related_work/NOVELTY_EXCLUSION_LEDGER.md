# Novelty exclusion ledger

| Candidate feature | Already covered or reducible? | Disposition |
|---|---|---|
| New proxy, CLIP prompt, fusion or embedding | Yes; ordinary retrieval and explicitly closed on the strict video | Rejected |
| More event-hypothesis graph state | Yes; EQUI-VOCAL/event-graph work and failed BCM state | Rejected |
| Fixed explore/exploit allocation | Yes; Seiden and failed P2 experiments | Rejected |
| Counterfactual materialization score | Existing BCM mechanism; measured contribution negligible | Rejected |
| Boolean hierarchical interval search | Classical group testing and closed ANY routes | Rejected |
| Longer clips with one answer | Ordinary retrieve-then-ground | Rejected |
| GPU batching alone | Systems optimization without new query semantics | Rejected |
| Proxy strata plus audit | Reducible to ABae/SUPG or the completed risk-limiting gate | Rejected |
| Workload cache alone | Materialized-view/predicate-cache territory | Rejected unless joined to new event semantics; current candidate fails feasibility gate |
| Variable-resolution set-valued enumeration plus relation-cover DP | Not found as a single algorithm in audited sources; combines known ingredients in a new query-plan problem | Retained provisionally as VERA |

For VERA, the novelty is not `EVENT_ENUMERATE` by itself. A VLM can plainly be
prompted to list events. The candidate survives only if its cover/ownership/
fallback optimization is necessary, formally specified, and empirically better
than fixed-window enumeration, ARC plus the same enumerator, and ordinary
retrieve-then-ground.
