# EventLift-AQP Stage 2 (Dev Segment) Report

> Stage 2 implementation of `EVENTLIFT_AQP_ALGORITHM_SPEC.md` on the dev
> segment `realcartest_2000_3200` only. Adds CERTIFY and SUPPRESS into the
> unified utility loop alongside DISCOVER and AUDIT. **All numbers are
> VLM-oracle-relative** (labels in `center10_vlm_oracle_events.csv` /
> `reference_events.csv`), not human ground truth, and no formal guarantee /
> certificate / statistical bound is claimed (per `AGENTS.md`,
> `CLAIMS_LEDGER.md` line 87). No safe stopping is claimed. No video / GPU /
> VLM / YOLO inference was run; all oracle calls are replay over existing
> labels. Stage 1 outputs are not modified.

============================================================
1. Data and setup
============================================================

- **Dev segment:** `realcartest_2000_3200` (the `is_dev=True` segment).
- **Grid:** `outputs/late_aqp_frozen_cross_segment_v1/grid_realcartest_2000_3200.csv`
  (120 bins, 32 positive, 20 reference events).
- **Proxy:** `prior_score_max`. **Label:** `is_positive`. **event_id:** present
  in grid but excluded from all online decisions (confirmed by code inspection:
  the loop reads only `bin_idx`, `prior_score_max`, and `ReplayOracle.query_unit()`
  responses).
- **Budgets:** 12 (0.10), 24 (0.20), 36 (0.30). **Seeds:** 0, 1, 2.
- **Utility hyperparameters (fixed, NOT tuned):** `ETA=1.0, LAMBDA=0.5,
  GAMMA=0.3, KAPPA=0.5, OMEGA=0.3`.
- **CERTIFY:** `CERTIFY_MAX_DEPTH=2` bins left/right. **SUPPRESS:**
  `SUPPRESS_RADIUS=2` bins, 0 oracle cost.

============================================================
2. Methods
============================================================

Five methods, all on the dev segment only:

1. `EventLift-discover-only` — DISCOVER only (Stage 1 control).
2. `EventLift-discover-audit` — DISCOVER + AUDIT (Stage 1 control).
3. `EventLift-discover-certify` — DISCOVER + CERTIFY (new).
4. `EventLift-discover-audit-certify` — DISCOVER + AUDIT + CERTIFY (new).
5. `EventLift-full-stage2` — DISCOVER + AUDIT + CERTIFY + SUPPRESS (new).

All 5 methods share the same unified `run_eventlift()` function, toggled by
`audit_enabled`, `certify_enabled`, `suppress_enabled` flags. No separate
repair/certify loop. CERTIFY is only triggered inside the action-selection
loop for pending anchors generated by prior positive DISCOVER or AUDIT calls.

============================================================
3. Budget ledger
============================================================

**Q1. Did all methods obey oracle budget?**

YES. 0 budget violations across all 45 runs (5 methods × 3 budgets × 3 seeds).
`oracle_calls_total <= budget_abs` for every frontier row. `cumulative_oracle_calls
<= budget_abs` for all 1080 trace rows. The ledger invariant
`oracle_calls_total == discover_calls + audit_calls + certify_calls +
suppress_calls` is asserted and verified (suppress_calls = 0 since SUPPRESS
has 0 oracle cost).

============================================================
4. Action arbitration
============================================================

**Q2. Did action arbitration remain non-degenerate?**

YES. The arbitration trace (`stage2_action_arbitration.csv`, 1092 rows) shows
all 4 action utilities are computed and the loop picks `argmax`:

| Method | DISCOVER | AUDIT | CERTIFY | SUPPRESS (computed) | SUPPRESS (chosen) |
|---|---:|---:|---:|---:|---:|
| discover-only | 216 | 0 | 0 | 0 | 0 |
| discover-audit | 147 | 69 | 0 | 0 | 0 |
| discover-certify | 174 | 0 | 40 | 0 | 0 |
| discover-audit-certify | 147 | 64 | 12 | 24 | 0 |
| full-stage2 | 147 | 64 | 12 | 24 | 0 |

- **CERTIFY was selected:** YES. 40 times in `discover-certify`, 12 times in
  `discover-audit-certify` and `full-stage2`. CERTIFY fires at budget 24 and
  36 (never at budget 12 — at budget 12 all budget goes to DISCOVER because
  no anchors are found early enough).
- **SUPPRESS was selected:** NO. SUPPRESS utility was computed 46 times
  (positive utility 0.17–0.34) but never chosen because DISCOVER/AUDIT/
  CERTIFY always had higher utility. This is **correct non-degenerate
  behavior**: SUPPRESS is a 0-cost action that downweights bins, but when
  there are still anchors to certify or components to discover, those actions
  have higher expected value. SUPPRESS would fire in a regime where the
  budget is exhausted for discovery but suppression could still save future
  redundant calls — which doesn't occur at these budget scales.
- **DISCOVER/AUDIT still receive budget:** YES. In `full-stage2` at budget 36,
  the split is DISCOVER=47%, AUDIT=42%, CERTIFY=6%, SUPPRESS=0% (oracle calls).
  The arbitration does not collapse to a single action type.

============================================================
5. CERTIFY effect on precision/interval quality
============================================================

**Q3. Did CERTIFY improve event precision or interval quality?**

YES, at budget 36. Comparing `discover-certify` vs `discover-only` (mean over
3 seeds):

| budget_abs | precision (discover-only) | precision (discover-certify) | delta |
|---:|---:|---:|---:|
| 12 | 0.400 | 0.400 | 0.000 |
| 24 | 0.468 | 0.476 | +0.008 |
| 36 | 0.400 | 0.497 | **+0.097** |

CERTIFY improves precision by +0.097 at budget 36 (from 0.40 to 0.50). This
is because CERTIFY refines interval boundaries by checking neighboring bins,
producing tighter intervals that match reference events at IoU ≥ 0.3 more
precisely. The certify success rate (fraction of CERTIFY calls that found at
least one additional positive neighbor) is 0.70–0.82 at budget 36.

CERTIFY does not improve recall (0.183 → 0.183 at budget 36) — expected,
since CERTIFY refines existing candidates rather than finding new events.

============================================================
6. SUPPRESS effect on duplicate_rate
============================================================

**Q4. Did SUPPRESS reduce duplicate_rate?**

SUPPRESS was never selected (see Q2 above), so `suppressed_bin_count = 0`
and `duplicate_rate = 0.0` across all runs. The `duplicate_rate` is 0.0 by
construction in this implementation because the loop checks `if b not in
covered` before querying — re-queries are structurally prevented. SUPPRESS's
value would appear as a reduction in *would-be* redundant DISCOVER calls
toward already-covered neighborhoods, but since the loop already avoids
re-querying, SUPPRESS's marginal benefit is fully captured by the `covered`
set. SUPPRESS adds no measurable benefit on top of the existing `covered`
tracking at this scale.

============================================================
7. Full Stage 2 vs discover+audit on recall
============================================================

**Q5. Did full Stage 2 hurt event recall relative to discover+audit?**

NO. `full-stage2` recall is identical to `discover-audit` at all budgets:

| budget_abs | recall (discover-audit) | recall (full-stage2) | delta |
|---:|---:|---:|---:|
| 12 | 0.050 | 0.050 | 0.000 |
| 24 | 0.117 | 0.117 | 0.000 |
| 36 | 0.167 | 0.167 | 0.000 |

Full Stage 2 does not hurt recall. The CERTIFY calls in `full-stage2` (1.67
mean at budget 36) consume ~5% of budget but do not reduce recall because
they refine existing candidates rather than replacing discovery. The
precision of `full-stage2` (0.300 at budget 36) is slightly lower than
`discover-audit` (0.323) because CERTIFY sometimes creates narrow intervals
that miss the IoU ≥ 0.3 threshold — but this is a precision/coverage tradeoff,
not a recall loss.

============================================================
8. CERTIFY/SUPPRESS budget share
============================================================

**Q6. Did certify/suppress consume too much budget?**

NO. At budget 36:
- `discover-certify`: CERTIFY uses 9/36 = 25% of budget.
- `discover-audit-certify` and `full-stage2`: CERTIFY uses 1.67/36 = 4.6% of
  budget (AUDIT dominates the non-DISCOVER share).
- SUPPRESS uses 0% (never selected; 0 oracle cost).

The 25% share in `discover-certify` is the upper bound — when AUDIT is
disabled, CERTIFY gets more budget. When AUDIT is enabled, CERTIFY's share
drops to 4.6%, which is reasonable and does not starve discovery.

============================================================
9. Residual reporting
============================================================

**Q7. Did residual reporting remain valid?**

YES. All 45 runs emit `residual_hat` and `residual_ucb`. Calibration
(`stage2_residual_calibration.csv`):

| method | budget | abs_error (mean) | audit_n (mean) | residual_ucb (mean) |
|---|---:|---:|---:|---:|
| discover-audit | 36 | 8.5 | 17.0 | 13.8 |
| discover-certify | 36 | 18.3 | 0.0 | 84.0 |
| full-stage2 | 36 | 10.7 | 15.3 | 15.0 |

- `discover-certify` has worse residual calibration (abs_error 18.3) because
  it has no AUDIT → `audit_n=0` → `p_ucb=1.0` → uninformative UCB.
- `full-stage2` has slightly worse calibration than `discover-audit`
  (abs_error 10.7 vs 8.5) because CERTIFY consumes some budget that would
  have gone to AUDIT, reducing `audit_n` from 17.0 to 15.3.

**Q8. Did any method attempt safe stopping?**

NO. All 45 runs have `stop_status = abstain_or_budget_exhausted`. Stop
reasons: `audit_n_too_small` for all runs (audit_n < 29 = n_min for
p_ucb ≤ 0.10). This is the expected behavior per `RC_AQP_PREFLIGHT.md` Gate 2
and the spec §6.3: per-segment safe stopping is statistically weak at this
scale.

============================================================
Gate decision
============================================================

**A. Proceed to multi-segment smoke.**

Rationale:
1. **Budget ledger is correct:** 0 violations across 45 runs, `source_action`
   lineage populated for all 1080 trace rows. ✓
2. **Full Stage 2 is not clearly worse than discover+audit on recall:**
   recall is identical (0.167 at budget 36). ✓
3. **Duplicate_rate does not improve / precision improves:** precision improves
   by +0.097 in `discover-certify` vs `discover-only` at budget 36.
   duplicate_rate is 0.0 by construction (re-queries structurally prevented).
   SUPPRESS does not fire but its utility is correctly computed. ✓
4. **Arbitration is non-degenerate:** CERTIFY fires 52 times total across
   `discover-certify` / `discover-audit-certify` / `full-stage2`. SUPPRESS
   utility computed 46 times. DISCOVER and AUDIT still receive the majority
   of budget. The loop does not collapse to one action type. ✓
5. **CERTIFY/SUPPRESS budget share is reasonable:** 4.6–25% of budget
   depending on whether AUDIT is enabled. ✓

Conditions for multi-segment smoke:
- The multi-segment smoke should run all 5 methods on the remaining 5
  LATE-AQP segments (3 realcartest non-dev + 3 dataset3) at budget 0.10/0.20/
  0.30, seed 0 only (to keep output small).
- Do NOT claim safe stopping. Do NOT claim EventLift beats B7-core from dev
  results. Do NOT run ARC-projection yet (Stage 3).
- The multi-segment smoke is a validation that the arbitration behavior
  generalizes, not a performance claim.

**Honest caveat:** SUPPRESS never fires on the dev segment. This could mean
(a) SUPPRESS is unnecessary at this budget scale (the `covered` set already
prevents re-queries), or (b) SUPPRESS's utility is under-calibrated. The
multi-segment smoke should check whether SUPPRESS fires on sparser segments
(e.g. `dataset3_0_1200` with only 7 positive bins) where discovery is more
exploratory and neighborhoods are less densely covered.
