# BCM-AQP v1 Phase-0 Blocker Report

Final decision: `ORACLE_PROVENANCE_BLOCKED_REQUIRES_BENCHMARK_V2`

## Outcome

Formal BCM experiments did not start.  BCM was not implemented.  Physical VLM
calls were zero.  No canonical, exploratory, ablation, ceiling, baseline, or
synthetic experiment was run.

The blocker is genuine input incompatibility at frozen unit 346:

- frozen interval: `[3457.93, 3462.93]`;
- cached interval: `[3457.866, 3462.866]`;
- start/end delta: `+0.064` seconds;
- frozen sample: 10 frames, decoded indices `103737,103752,…,103872`;
- cache sample: 11 frames, decoded indices `103735,103750,…,103885`;
- decoded-frame index sequences under the recovered arithmetic: unequal;
- current OpenCV 4.13 exact-code replay RGB-content sequences: unequal.

Therefore the old frozen baseline cannot be mixed with an oracle corrected to
the frozen interval.  A new benchmark ID and a compatible baseline rerun are
required before any formal BCM comparison.

## Decisive evidence

The original cache-generation code and configuration path were recovered:

- 297 Stage-2 raw responses were generated by
  `stage2_full_center10_oracle.py`;
- 50 raw responses were reused from the P1 script `run_pilot_oracle.py`;
- both use the same OpenCV `VideoCapture` frame-selection loop;
- unit 346 belongs to the Stage-2 set;
- source raw JSON, frozen raw copy, and cache-manifest hashes match for all 347
  units;
- video SHA256 and prompt SHA256 match for all 347 units.

Read-only current-environment replay of that exact selection loop found
identical decoded indices and content for units 0–345 and different
indices/content for unit 346 only.  Generation-time decoder bytes were not
retained, so historical RGB arrays cannot be cryptographically re-hashed; the
different historical requested interval and deterministic frame-index
arithmetic independently establish a genuinely different input.
The per-unit table is `audit/oracle_cache_interval_audit.csv`; exact unit-346
frame/timestamp/content pairs are `audit/unit346_frame_equivalence.csv`.

## Root cause

The original anchor builder hard-coded `3462.866`, the ffprobe video-stream
duration.  The clean proxy precompute instead used MP4
`format.duration=3462.930499`.  Both clip the final center-10 anchor to their
chosen duration and format it to milliseconds, producing 3462.866 versus
3462.930.  The original loader then applies `int(timestamp * video_fps)` with
OpenCV FPS `30.000005775562784`; the shifted start crosses two frame indices.

Thus:

- float formatting is not the root cause;
- format-versus-stream duration plus final-unit clipping is the root cause;
- truncating frame-index conversion propagates it into different content;
- separate video-loader behavior and different video bytes are rejected;
- no timestamp tolerance was introduced.

High temporal overlap and the negative cached label were not used to excuse the
mismatch.

## Theory/code audit result

The clean benchmark helper previously described as missing is present.  Its
file SHA256 is
`0a7a8ad4a13cc4404b0cfe7dfb1aef8958197267e22ff1df545ac4dbbf744610`.

The exact M0/M1 distinction is:

- M0 `original_k3`: join when the number of intervening unit IDs is at most
  `g_max=1`, no queried negative occupies that bridge, and duration passes;
- M1 `k3_bridge_safe`: join only immediately adjacent positive unit IDs, with
  the same duration and barrier checks.

Both test span against `min(d_core_max,d_seg_max)+1e-9`; under 40/60 seconds,
40 binds and 60 is redundant.  Positive-anchor coverage holds for both on
valid unique-unit traces.  Negative barriers substantively split M0 bridges;
M1 adjacency makes its bridge-negative check vacuous.

The matcher performs Hungarian assignment on
`1000*overlap_any + temporal_iou`.  For this frozen event count it is
cardinality-first then summed-tIoU.  Exact equal-objective assignment ties have
no repository-defined secondary key beyond solver/row-order behavior.  Event
F1 uses any strict positive overlap retained by one-to-one assignment.  AUC is
normalized trapezoidal integration over the available sorted budgets, intended
as `[5,10,20,50,80,100]`, with no zero-budget point.

Full source paths, symbol/file hashes, pseudocode, canonicalization behavior,
OracleAccessor, trace replay, invariants, and all remaining disagreements with
`BCM_AQP_MATHEMATICAL_REFERENCE.md` are documented in
`audit/THEORY_CODE_AUDIT.md`.  The mathematical reference was not modified.

## Provenance limitations beyond the decisive mismatch

The original scripts record paths and raw responses but not generation-time
hashes for model weight bytes, processor packages/config, qwen video processor,
full generation defaults, or parser source.  P1 and Stage 2 also use different
JSON regexes.  Current path/config lineage agrees, prompt and raw-response
hashes match, but that is not contemporaneous cryptographic proof.  For this
reason content-identical rows 0–345 remain conservatively unresolved rather
than being promoted to an approved content-equivalent decision.

This uncertainty cannot reverse the global conclusion because unit 346’s
different requested indices and decoded contents independently satisfy the
benchmark-v2 decision rule.

An independent read-only adversarial review supported the benchmark-v2
decision and verified the code semantics, source hashes, root-cause chain, and
unit-346 usage counts.  Its schema/environment, reproduction, historical-RGB
wording, and nested-response-hash findings were all fixed before final

`audit/INDEPENDENT_REVIEW.md`.

## Required next action

Do not start BCM against benchmark v1.  Under separate explicit authorization,
define one authoritative video-duration convention, create a compatible unit
grid/oracle with generation-time environment hashes, issue a new benchmark ID,
and rerun compatible baselines.  Only then can formal BCM runs begin.
